# 整理洗版与 STRM 同步

状态：首版已实现于整理流程。日期：2026-10-04。既有目录默认关闭，需要用户启用。

## 使用

1. 进入目录的整理页，点击「洗版策略」，或在新建/编辑目录时打开同名页签。
2. 选择「画质优先」「兼容优先」「节省空间」预设，开启洗版并保存。规则支持拖动、上移/下移；首条命中决定档位。配置修改后重新预览。
3. 查看「洗版处理」列，展开查看旧文件、新旧 STRM 路径和清理项。只有「新增」「替换旧版」可执行。
4. 关闭预览模式，核对当前引擎的计划后执行。执行中断时在「洗版记录」继续或恢复；重启后的执行租约最多等待 5 分钟，运行期间自动续期。

保存策略不会直接改动媒体库。洗版保留原始下载目录及未选文件，便于失败恢复；旧视频和对应云盘字幕、文件级 NFO/媒体信息放在 `/FilmFusion-Recovery/<任务 ID>/<原目录 ID>/`。旧 STRM、字幕和文件级元数据内容保存在数据库恢复记录中。不会自动永久删除恢复副本，已完成任务不开放自动回退，避免回退覆盖后续整理。

## 与 MP2 的关系

参考 MoviePilot `v2.15.6`，提交 `1528176beacc0f9f8d8d9cbf1adf048b0da67b5c`。Wiki 已包含部分 V3 内容，V2 行为以固定提交为准：

- [进阶文档](https://wiki.movie-pilot.org/zh/advanced)：从上到下匹配，第一个命中决定优先级。
- [过滤器](https://github.com/jxxghp/MoviePilot/blob/1528176beacc0f9f8d8d9cbf1adf048b0da67b5c/app/modules/filter/__init__.py#L269)：UI 的第 1、2、3 档对应内部优先级 100、99、98。
- [订阅洗版](https://github.com/jxxghp/MoviePilot/blob/1528176beacc0f9f8d8d9cbf1adf048b0da67b5c/app/chain/subscribe.py#L550)：分集筛选严格提升的候选。
- [文件整理](https://github.com/jxxghp/MoviePilot/blob/1528176beacc0f9f8d8d9cbf1adf048b0da67b5c/app/modules/filemanager/transhandler.py#L432)：覆盖策略独立于订阅优先级。

FilmFusion 使用有序档位，另提供同档权重和最小提升分数。权重不会跨越档位；这部分是本项目的实现，不是 MP2 配置格式兼容层。

## 比较规则

- 同一用户、存储和整理目录下，按媒体类型、TMDB、最终目标季集、Part、剪辑版区分身份。S00 有效；一个文件包含多集时进入待确认。
- 原始文件名通过 medianame 提取分辨率、片源、编码、特效和制作组。质量判断不切换当前预览所用的 MP2/medianame 识别与命名引擎。
- 字段内多个值为任一匹配，不同字段之间同时满足。「名称包含」是大小写不敏感的字面包含，不执行正则或脚本。
- 排除项和单文件大小限制先于档位判断。大小单位为 1024² 字节。未知大小无法满足大小限制；质量字段不足或旧版无法命中档位时待确认。
- 同档默认保留已有。启用同档升级后，分数提升必须达到阈值，平分不会替换。一个加分规则命中多个标签也只加一次。
- 新旧文件均按本次冻结策略重新计算；不比较历史旧分数与新策略分数。整理成功后保留原始质量证据，重命名丢失标签不会丢失该证据。
- 同批同一身份只选出一个可执行候选。不同身份写入同一 STRM/字幕路径时待确认。前端不可勾选的记录，后端同样拒绝强行提交。

预设是可编辑起点：画质优先按分辨率、片源排序；兼容优先偏好 H.264 并排除 Dolby Vision；节省空间偏好 1080p/720p 的高效编码并限制单文件 20 GiB。预设不承诺适配所有设备，名称标签也不代表已探测真实码流或字幕。

## 旧版发现与绑定

预览读取受影响的影片/季目录，结合已登记文件和现有本地 TMDB 目录回退定位旧版。已有云盘文件需要可验证的 TMDB 目录标记，或匹配文件 ID、pickcode、大小和路径的登记记录。仅本地目录存在不足以允许替换。

STRM 绑定包含目录自身的保存路径、同账号匹配的 CloudPath 映射，以及先前登记的实际绑定。已登记的旧配置即使变更前缀或映射，仍可找到旧 STRM。无法证明归属、内容被其他操作修改、目标路径冲突或路径越过保存根目录时停止并显示原因。

| 场景 | 处理 |
| --- | --- |
| 同名替换 | 原子写入 STRM，更新文件 ID 与 pickcode，停用旧 302 播放分配 |
| 改名/改路径 | 先安装新 STRM，再移除属于旧文件的入口 |
| 多份 STRM | 更新所有匹配且受管理的绑定，记录各自原内容 |
| 旧字幕 | 仅处理与旧视频准确同名或带已知语言修饰的外挂字幕，不假设新旧时间轴相同 |
| 新字幕 | 执行前下载并核验大小，写入恢复记录后再进行文件替换；不加入异步字幕队列 |
| 文件级 NFO、mediainfo | 保存恢复内容后清理，避免新版继续使用旧码流信息 |
| 共享资料 | 保留 `movie.nfo`、`tvshow.nfo`、海报等共享文件，不整目录删除 |

关联本地文件和新字幕限 2 MiB；超过限制待确认。新字幕获取使用 115 Open 令牌。STRM 和字幕在同目录写临时文件后 rename；路径访问使用 `os.Root`，限制符号链接越界。

## 执行和恢复

云盘、磁盘和数据库无法跨系统原子提交，执行器以持久化记录、文件 ID 查询和幂等写入逐步推进：

1. 沿用服务端不可变整理计划，保存策略、源目录清单、库内目录清单和关联本地文件快照。
2. 实际执行前重新校验源文件、目标目录和 STRM，按存储账号互斥，防止同账号整理相互覆盖。
3. 建立恢复记录，取得字幕内容，解析新目录与恢复目录；这些准备完成并保存前不移动文件。
4. 同名旧文件先进入恢复目录，再将新文件重命名/移动到位。每次操作前后读取文件 ID、名称、大小、pickcode；请求超时但实际成功时按实际状态继续。
5. 写入新入口，更新媒体登记和 pickcode，停用旧 302 分配；旧副账号文件保留原清理信息，不再按原路径复用。
6. 清理旧入口，将其余旧文件移入恢复目录。失败保留账号锁，用户可继续或反向恢复。恢复时也校验文件状态，拒绝覆盖其他操作的新改动。
7. 完成后释放账号锁。若已配置 Emby，提交媒体库刷新；刷新失败独立记录，支持「重试 Emby 刷新」。提交成功不代表 Emby 已完成扫描或播放验证。

任务有运行令牌和续期租约。继续/恢复通过原子认领校验状态及原记录；旧请求不能改写新请求的任务状态。恢复一旦开始，后续重试继续恢复。

迟到的 STRM 创建/删除事件会检查管理记录及云盘实际文件，保护仍在使用的入口；恢复目录不会参与 FilmFusion 的 STRM 扫描。旧下载任务也检查路径是否已由洗版接管，不能在恢复后写回旧内容。外部媒体工具需要自行排除恢复目录。

## 代码与接口

- `app/service/media_upgrade_policy.go`：策略、预设、证据和比较。
- `app/handler/organize_upgrade_preview.go`：旧版发现、绑定、计划。
- `app/handler/organize_upgrade_execute.go`：互斥、替换、缓存和恢复。
- `app/service/media_upgrade_files.go`、`media_upgrade_subtitle.go`：本地文件快照、原子写入、字幕获取。
- `app/service/organize_upgrade_guard.go`：延迟事件和下载归属检查。
- `app/model/organize_upgrade.go`：媒体登记、入口绑定、账号锁和恢复记录；启动时自动迁移。
- 目录配置字段：`upgrade_policy`，JSON 字符串；空值/未启用沿用原整理。
- `GET /api/organize/upgrade/presets`、`POST /api/organize/upgrade/test`：预设及质量规则试算。
- `GET /api/organize/upgrade/jobs?cloud_directory_id=...`：当前用户最近 50 条记录。
- `POST /api/organize/upgrade/jobs/:id/retry`，请求 `{ "restore": false }` 继续，`true` 开始恢复。
- `POST /api/organize/upgrade/jobs/:id/refresh`：已完成任务单独重试 Emby 刷新。

## 首版范围与验证

首版入口为现有整理计划；自动化若调用同一整理入口，也遵循对应目录的策略。没有增加主动搜索、订阅下载洗版、全库扫描登记、独立策略库、停止阈值或永久清理调度。

旧版查找限定于目标目录、已登记位置及现有本地目录回退，不承诺发现整盘任意改名的历史文件。外部未登记的 STRM、插件独立元数据目录不会被盲目清理。多集文件和无法判定的版本保留待确认状态，首版不提供绕过判断的强制覆盖按钮。

已用模拟 115、临时 SQLite 和临时本地目录覆盖：预览不写文件、高低档与权重阈值、同名/改名替换、多映射、字幕和 NFO、pickcode/302 失效、云盘请求成功但响应丢失、源/目标/策略/本地文件变化、移动失败后的继续/恢复、跨用户重试拒绝、迟到 webhook 与旧下载拦截。前端测试覆盖预设不自动启用、规则重排、后端试算，以及整理确认时保留源目录。

本次验证通过后端全量 473 个顶层测试、洗版相关竞态检查、整理洗版用例连续 10 轮、前端相关 19 个测试，以及 Go 构建、TypeScript 检查和前端生产构建。SQLite 任务认领采用单次条件更新，管理记录事务先取得写锁，避免与日志写入发生读锁升级冲突。

浏览器核对使用真实 React 组件与模拟接口。没有执行真实 115 文件替换或 Emby 播放验收，未部署。
